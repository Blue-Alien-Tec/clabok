## 0. Current state and pre-planned decisions (2026-11-05)

Already implemented and to be used:

- `store.LoadRegistry` / `Registry.Save`: v1 `{version, books:[{id, path, kind}]}`. `path` is the
  output **directory** relative to the project. The library entry uses `.` (README at the project
  root); a regular book uses e.g. `Docs/guide`.
- `render.Service.Sync(book, outputDir, SyncOptions)`; `library sync` loops the registry and calls it
  per book with `--check`/`--write`/`--prune`/`--force`.
- `lifecycle.FromEnv`, `RequireClosed` and `State` for wiring and the open-book guard.
- IDs are immutable; there is no rekey. `move`/reparent change only the ordered collections, so
  references stay valid.
- `store.OpenBookCount` and the config mode guard already exist.
- `config.Values` exposes ProjectDir, StoreRoot, DocsRoot, UndoLimit and BookPointLimit.

Pre-planned decisions:

- `book new --id <id> --title <t>` creates the container from `model.NewManifest`, saves it closed,
  registers `{ID, Path: <docs-root-relative>/<slug>, Kind: "book"}`, and copies the library defaults
  into the manifest settings at creation (the model cannot express "unset").
- `library` command group: `library sync`, `book new`, `book move`, `book rename`,
  `book unregister`. Unregister deletes nothing; it removes only the registry entry.
- The library book is the registry entry with `Kind: "library"` and `Path: "."`; its monolith render
  is the repository `README.md`.
- Cut-over: create the library book from the current README content (structure plus blocks), render,
  and require `sync --check` clean. Do not touch legacy books.
- Open books cannot move, rename or unregister (`lifecycle.RequireClosed`).
- Render is the sole read path that bypasses the open state: it reads a closed book's container
  read-only, so the library-wide sync never opens a book. Body and structure mutations still require
  `open` (`PLAN.md` §3.5).
- IDs are issued by the library ledger and never change. A duplicate owned ID is corruption:
  `sync --check` rejects it with the ID and the affected books instead of renaming anything.

## 1. Goal

Make the library the structural authority over its books, create new books under the configured docs
root, and cut the CLABOK `README.md` over to a book generated by `pecia` — proving the model on a
real book while the legacy books stay untouched.

## 5. Acceptance criteria

1. `book new` creates a book under the configured docs root, registers it, and renders its README in
   the default monolith mode.
2. A book created outside the docs root is either refused or explicitly allowed by a named flag;
   there is no silent third location.
3. The library README renders at the project root, carries `[Document Index]` navigation at the top
   and bottom, and contains the Document Index of all registered books in registry order.
4. Library defaults apply to a book that has no explicit value; a per-book value wins.
5. Library sync renders every registered book and reports per-book drift without writing under
   `--check`.
6. Moving or renaming a registered book updates the registry and its output path and leaves its
   container and bodies unchanged; both are refused while the book is open, as is unregister.
7. No command in the new tool opens, lists or modifies a legacy container (integration test with a
   fake legacy directory proves it is ignored).
8. The cut-over milestone passes: `pecia sync --check` is clean on the CLABOK repository, the README
   is generated (not hand-edited), and a change to a body renders through `sync --write`.
9. `library` has no command that imports or adopts an existing book.

## 6. Design decisions for this scope's planning session

- Registry schema and its version, and the migration/refusal policy for an older registry.
- Where the library's own policy fields live (registry entry versus a separate library manifest).
- Book ID derivation (slug, sequence) and how it relates to the output path; renaming a book versus
  renaming its folder.
- The exact `book new` flag set for the opt-ins (numbering, toc, index depth, output mode) and which
  of them are library defaults versus per-book overrides.
- Whether `Docs/<slug>` is one folder per book with generated files directly, or a subfolder per mode.
- What the scaffold README keeps (checks section, release note) and whether those become blocks of the
  library book.
- Whether unregister deletes anything (default: nothing) and what it does with an orphaned output
  folder.
- Whether the Document Index is generated from the registry or from the layout block sources, and how
  the two are kept consistent.

## 7. Risks and constraints

- The hard cut is the core risk control of this plan. Do not add an import path "just in case"; it
  reopens migration complexity.
- The README is the project's front page. Treat the cut-over as a deliberate content migration of the
  scaffold text, not as an automatic conversion of the old DocEngine library.
- Library defaults plus per-book values form a two-level configuration. Test the precedence, because
  the failure is silent (a book renders with the wrong mode).
- An open book must not move. The registry update and the file move are two steps; the guard belongs
  before either.
